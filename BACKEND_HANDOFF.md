# Bookey backend handoff

This document is for the developer building the FastAPI backend. The frontend is
complete against mocks. Your job is to replace the mock sources listed here
without changing UI components.

## 1. Mock client replacement point

All realtime reader traffic goes through **one interface**:

- Interface: `lib/contracts/book-client.ts` → `BookClient`
- Protocol types: `lib/contracts/book-events.ts`
- Runtime guard: `lib/contracts/validate.ts` → `parseServerEvent()` (every inbound frame is validated, and invalid frames are dropped)
- Shared base: `lib/book-client/base-client.ts` (listeners, validation, typed send helpers)
- **WebSocket client:** `lib/book-client/websocket-book-client.ts` — already implemented with reconnect, exponential backoff + jitter (max 30 s), heartbeat (30 s interval, 10 s timeout), and session resume by sessionId + last seq
- **Swap point:** `createBookClient()` in `lib/book-client/index.ts`

To go live, set `NEXT_PUBLIC_BOOKEY_CLIENT=ws` and `NEXT_PUBLIC_BOOKEY_WS_URL=wss://your-api/ws/book`.
The `WebSocketBookClient` is selected automatically. No component changes needed.

Components use `useBookClient()` / `useBookEvent()` from `lib/book-client/react.tsx`.

`lib/book-client/fixtures.ts` contains seeded frame sequences. You can replay them
against the client to compare backend output with what the UI expects.

## 2. Realtime event contract (WebSocket)

Envelope, server → client:

```json
{ "v": 1, "type": "text_chunk", "seq": 42, "sessionId": "sess_abc", "ts": 1790000000000, "payload": {} }
```

Envelope, client → server:

```json
{ "v": 1, "type": "start_page", "payload": {} }
```

- `v` must equal `BOOK_PROTOCOL_VERSION` (1). Other versions are rejected.
- `seq` increases monotonically per connection. Lower values are stale, and a gap means frames were dropped.
- `sessionId` is `null` for connection-level frames.

### Client → server

| type | payload |
| --- | --- |
| `start_page` | `{ courseId, pageId }` |
| `pause` / `resume` | `{ sessionId }` |
| `seek` | `{ sessionId, segmentId, wordIndex }` |
| `speed` | `{ sessionId, value }` (0.75–2) |
| `ask_question` | `{ sessionId \| null, source: 'voice'\|'text', text, questionId, context: { courseId, pageId, language: 'tanglish'\|'tamil'\|'english' } }` |
| `run_code` | `{ courseId, pageId, code, language: 'python', codeId, stdin?, useSampleInput? }` |
| `submit_survey` | `{ courseId, answers: Record<string,string> }` |

`questionId` and `codeId` are generated by the client. Echo them in every reply.

### Server → client

| type | payload | UI consumer |
| --- | --- | --- |
| `session_started` | `{ sessionId, courseId, pageId }` | narration stream |
| `text_chunk` | `{ segmentId, text, wordStart, wordEnd, audioStartMs }` | narration text, word highlight, diagram step derivation |
| `audio_chunk` | `{ segmentId, mime, base64, seq, final }` | reserved. Wire into `lib/narration/audio-player.ts` (currently a silent seam) |
| `cue` | `{ segmentId, atWord, action: 'draw'\|'highlight'\|'runCode'\|'showOutput', targetId }` | dev panel. Reader derives cues locally today |
| `diagram_spec` | `{ diagramId, spec: DiagramSpec, steps }` | reserved for a backend-driven diagram renderer |
| `diagram_draw` | `{ diagramId, stepId }` | same |
| `highlight` | `{ targetId, style: 'marker'\|'ring'\|'underline' }` | same |
| `code_stream` | `{ codeId, chunk, final }` | reserved |
| `run_result` | `{ codeId, stdout, stderr, status: 'success'\|'error', durationMs, trace? }` | code lab |
| `question_received` | `{ questionId, source, text }` | tutor |
| `answer_chunk` | `{ questionId, text, final, attachments?: { code?, diagram? } }` | tutor (streamed) |
| `sources` | `{ questionId, items: SourceItem[] }` | tutor citations |
| `scope_refused` | `{ questionId, message }` | tutor refusal state |
| `page_complete` | `{ pageId }` | narration end, progress |
| `error` | `{ code, message, recoverable }` | error banners/toasts |

**Important:** the reader currently computes diagram steps, highlights and cue
actions locally from the page data plus the active `text_chunk.wordStart`. That
keeps them correct during seek. The backend must therefore send accurate
`wordStart`/`wordEnd` indices that match the page's narration script.

Separate analytics drafts (`page.viewed`, `page.completed`, `bookmark.toggled`,
`note.saved`, `survey.answered`) live in `lib/contracts/events.ts`. They're meant
for a batched `POST /events`, not the socket.

## 5. Expected data schemas

Learner course (`lib/mock/learning.ts`). This is the shape the learner UI renders:

```ts
interface LearningCourse {
  id: 'python' | 'java' | 'machine-learning' | 'web-development' // slug-like id used in URLs
  title: string; subtitle: string; description: string
  level: 'Beginner' | 'Intermediate' | 'Advanced'
  category: 'Programming' | 'Data & AI' | 'Web'
  language: string
  available: boolean
  author: string
  cover: { base: string; spine: string; accent: string; text: string }
  chapters: { number: number; title: string; pages: number; summary: string }[]
  outcomes: string[]; topics: string[]
  project: { title: string; description: string }
  tutorStyle: string
  completedPages: number        // per user, move to progress
  lastOpened: string | null     // per user
  minutesPerPage: number
  resumeExcerpt: string
}
```

Page counts shown anywhere in the UI are **derived** (`getCoursePosition`, which
sums `chapters[].pages`). Never store a separate total. Current seed totals:
Python 70 pages / 9 chapters (38 done), Java 82 / 11 (12 done),
Machine Learning 88 / 10 (5 done), Web Development 73 / 11 (unavailable).

Reader lesson page (`types/book.ts` → `BookLessonPage`). Each page contains the
title, body blocks, a narration script split into segments with word indices,
`NarrationCue[]` (`highlight-term` | `focus-node` | `focus-code-line` at a word
index), an optional `CodeExample` (code, sample inputs, expected output) and an
optional `DiagramSpec` (`types/diagram.ts`: nodes, edges, groups, annotations,
highlights and ordered steps).

Legacy catalog (`types/learning.ts`): `Course`, `Chapter`, `BookPage`,
`CourseProgress`, `AppNotification`, `AdminMember`. IDs are prefixed template
literals (`course_…`, `chapter_…`, `page_…`, `user_…`, `notif_…`).

**Recommendation:** unify both models server side around
`Course → Chapter → Page` with stable string ids, and keep per-user state
(`completedPages`, `lastOpened`, bookmarks, notes) in separate progress tables.

## 6. Non-goals of the frontend

The frontend never stores secrets, never calls an AI provider directly and
never executes arbitrary code. Code execution, TTS, retrieval and tutor answers
are backend responsibilities. The frontend only renders their frames.
